# Как объяснить лабораторную №7

Начни с одного маршрута запроса, затем объясни детали нужного класса. Не нужно запоминать весь проект подряд.

## Порядок чтения исходников

1. **common/models/RouteData и Route.** RouteData содержит поля, которые вводит пользователь. Route содержит также ID, дату и владельца. Это не позволяет клиенту назначить себе чужого владельца.
2. **common/network/CommandRequest и Credentials.** В запросе находятся команда, аргументы, учётные данные и UUID.
3. **server/server/RequestHandler.** Входная точка бизнес-обработки: проверка пользователя и защита от повторов.
4. **server/commands/CommandRegistry.** Команда сопоставляется с обработчиком ServerCommand.
5. **server/service/CollectionService.** Здесь находятся права владельца, условия команд и синхронизация памяти с БД.
6. **server/repository/PostgresRouteRepository и db/Database.** Здесь SQL и границы транзакции.
7. **server/server/UdpServer и client/client/CommandSender.** Здесь потоки, UDP и повторная доставка.
8. **client/client/InputStack и RouteReader.** Здесь пользовательский ввод и скрипты.

Пути выше обозначают модуль/пакет/класс; исходники находятся в src/main/java соответствующего модуля.

## Пример: пользователь выполняет add

1. ClientApp проверяет, что на клиенте сохранены Credentials после register/login.
2. RouteReader собирает RouteData и проверяет поля.
3. ClientApp создаёт CommandRequest. Его UUID идентифицирует одну логическую попытку команды.
4. CommandSender сериализует запрос, разбивает на UDP-фрагменты и отправляет DatagramChannel.
5. Сервер читает датаграммы в отдельном Thread, собирает сообщение и читает объект в новом Thread.
6. CachedThreadPool обработки запускает RequestHandler.
7. AuthService ищет login в users и проверяет SHA-256 пароля. Сервер получает ID пользователя.
8. RequestJournal проверяет, не выполнялся ли уже этот UUID с теми же данными.
9. CommandRegistry выбирает обработчик ADD.
10. CollectionService захватывает монитор синхронизированной коллекции.
11. PostgresRouteRepository делает INSERT без передачи ID; PostgreSQL берёт ID из sequence.
12. RETURNING возвращает поля сохранённого маршрута. Database выполняет COMMIT.
13. Только после возвращения из транзакции CollectionService добавляет Route в TreeSet и индекс byId.
14. Отдельный CachedThreadPool отправляет ответ клиенту.

## Где выполнено каждое требование

| Требование | Реализация |
|---|---|
| Хранение в PostgreSQL | PostgresRouteRepository, schema.sql |
| ID через sequence | DEFAULT nextval, INSERT без id, RETURNING |
| Память после успешной записи | Database.transaction + CollectionService |
| Чтение коллекции из памяти | snapshot, info; CommandRegistry использует их |
| Регистрация и вход | AuthService, PostgresUserRepository, REGISTER/LOGIN |
| SHA-256 | PasswordHasher |
| Запрет команд без авторизации | RequestHandler.authenticate перед dispatch |
| Хранение создателя | routes.owner_id, Route.ownerId |
| Изменение только своего | CollectionService.owned, фильтр владельца, SQL WHERE owner_id |
| Логин и пароль в каждом запросе | CommandRequest.credentials |
| Чтение через Thread | UdpServer.readRequests, readCommand |
| Обработка через CachedThreadPool | UdpServer.processing |
| Отправка через CachedThreadPool | UdpServer.sending |
| Collections.synchronizedXXX | synchronizedNavigableSet в CollectionService |

## Почему нужны два класса Route и RouteData?

У клиента ещё нет ID нового маршрута. ID появляется после INSERT в БД. Если клиент передавал бы полноценный Route, ему пришлось бы подставлять фиктивный ID, дату и владельца.

RouteData выражает только входные данные. Route выражает уже сохранённую запись. При update ID задаётся аргументом команды; дата создания и владелец сохраняются.

## Почему sequence, а не max(id) + 1?

Два параллельных запроса могут увидеть одинаковый max(id). Sequence выдаёт разные значения независимо от таких гонок. Она не обязана выдавать номера без пропусков: rollback не возвращает выданное значение назад.

## Почему недостаточно synchronizedSet без synchronized-блока?

Обёртка защищает отдельные вызовы add/remove/size. Она не делает атомарным сочетание «найти минимум, сравнить, сохранить, добавить».

Кроме того, iterator и stream требуют внешней синхронизации на той же обёртке. Поэтому CollectionService использует synchronized(routes) для обходов и составных операций.

## Почему блокировка держится во время SQL?

Если отпустить её перед commit, второй запрос может принять решение по старому состоянию памяти. Например, два одинаковых add_if_min одновременно пройдут проверку.

Под одной блокировкой условие проверяется относительно последнего завершённого изменения. После commit меняется память, затем блокировка освобождается. Это простое решение с последовательными записями; многопоточность при этом сохраняется на уровне чтения сети, авторизации, обработки других запросов и отправки.

## Чем SQL-транзакция отличается от synchronized?

synchronized управляет доступом потоков к Java-объектам внутри одного JVM. Транзакция управляет атомарностью и сохранностью изменений в PostgreSQL.

Нужны оба механизма: один защищает память программы, второй — записи БД. Для массового удаления все выбранные строки удаляются одной транзакцией. Если удаление одной строки нарушило ограничение, rollback восстанавливает все предыдущие удаления этой транзакции.

## Что происходит, если PostgreSQL недоступен?

Если ошибка случилась до успешного commit, память не меняется. Если связь потеряна во время commit, сервер не может достоверно определить результат. Он прекращает работу с коллекцией до перезапуска и загрузки фактических данных.

БД является постоянным хранилищем, память — рабочим представлением для команд чтения. После аварийного завершения сервер загружает коллекцию заново.

## Как определяется владелец?

По логину и паролю сервер находит строку users и получает её ID. Клиент не передаёт ownerId как доверенное значение.

При update/remove_by_id сервис проверяет владельца найденного Route. clear и условные удаления выбирают только свои маршруты. SQL дополнительно проверяет owner_id, поэтому защита присутствует и на уровне записи.

show и фильтрация видят все маршруты.

## Зачем соль, если в задании написано SHA-256?

Алгоритм хеширования остаётся SHA-256. Перед паролем добавляются 16 случайных байтов соли, чтобы одинаковые пароли не давали одинаковые сохранённые значения.

В базе лежит saltHex:hashHex. При входе соль читается, хеш вычисляется снова и сравнивается. Хеширование не является шифрованием: обратного метода «расшифровать пароль» нет.

Для реальных систем обычно выбирают специальные медленные алгоритмы хеширования паролей. Здесь SHA-256 выбран в соответствии с заданием.

## Почему пароль проверяется в каждом запросе?

Так требует задание. После login клиент сохраняет Credentials в оперативной памяти и прикладывает их к последующим запросам. Сервер не доверяет одному факту предыдущего входа.

EXIT и EXECUTE_SCRIPT обрабатываются локально. Скрипт сам не отправляется серверу: клиент читает его команды и отправляет каждую с учётными данными. До входа клиент не запускает скрипты. Сервер отдельно проверяет все полученные команды независимо от клиента.

## Почему отдельное соединение на операцию?

Один Connection нельзя использовать как общий контекст независимых транзакций: потоки могли бы смешать autoCommit, commit и rollback.

ConnectionFactory открывает отдельное соединение для операции. Database закрывает его через finally. Семафор ограничивает число одновременных соединений. Это не пул соединений: соединения здесь не переиспользуются.

## Что даёт CachedThreadPool?

Он создаёт рабочие потоки по необходимости и переиспользует освободившиеся. Простаивающие потоки со временем завершаются.

Пулы обработки и отправки независимы: ожидание отправки не занимает обработчик команды. Семафор ограничивает общее число запросов, чтобы бесконечный поток клиентов не создавал неограниченное число потоков.

## Зачем UUID, если UDP уже передаёт адрес и порт?

Адрес и порт определяют клиента, но не конкретную команду. Ответ может задержаться, потеряться или прийти после повторной отправки.

Один UUID сохраняется при повторах. Сервер хранит ответ и не выполняет ту же команду заново. Другие данные с тем же UUID отклоняются. Журнал ограничен памятью и временем, после перезапуска исчезает: это не постоянная гарантия exactly-once.

## Почему нужен разбор фрагментов?

Одна UDP-датаграмма не может содержать произвольно большой show. Протокол разбивает сообщение на небольшие части, помечает номер, общее количество и UUID.

Получатель собирает части даже при перестановке и дубликатах. Недостающие части приводят к повтору запроса. Ограничение размера и квота памяти защищают от накопления бесконечных незавершённых сообщений.

## Почему проверяются данные при десериализации?

Обычный Java-конструктор не вызывается при стандартной десериализации Serializable. Проверки только в конструкторе не защищали бы сервер от некорректного сетевого объекта.

readResolve создаёт проверенный экземпляр через конструктор. ObjectInputFilter дополнительно ограничивает допустимые классы, глубину графа, количество ссылок и размер массивов.

## Как сравниваются маршруты?

Для порядка TreeSet сначала сравнивается distance, затем id. Поэтому разные маршруты с одинаковой дистанцией не теряются.

Для условных команд сравнивается только distance: RouteData ещё не имеет ID. NULL стоит перед любой заданной дистанцией. equals и hashCode Route согласованы с ключами естественного порядка; уникальность ID дополнительно обеспечивают БД и индекс byId.

## Что показать преподавателю

1. Запустить сервер, открыть два клиента.
2. Зарегистрировать разных пользователей.
3. Первым добавить маршрут, вторым увидеть его через show.
4. Вторым попробовать update/remove_by_id чужого ID и получить отказ.
5. Добавить маршруты обоих пользователей; показать, что clear удаляет только свои.
6. Перезапустить сервер и проверить, что оставшиеся маршруты загрузились из PostgreSQL.
7. Показать users.password_hash и routes.owner_id в БД, не показывая пароль подключения.
8. Открыть UdpServer, CollectionService и Database и объяснить разделение потоков и commit.
9. Запустить тесты. Интеграционные тесты используют отдельные таблицы и не очищают рабочую коллекцию.
