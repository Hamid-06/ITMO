# Лабораторная работа №7 — Route

Java 17, Maven, PostgreSQL, UDP. Проект продолжает вариант лабораторной №6 с коллекцией маршрутов.

В репозитории ITMO проект находится в `Programming/Lab7`. Команды сборки и запуска ниже выполняются из этого каталога.

## Быстрый запуск на компьютере

Зависимость PostgreSQL JDBC находится в **server/pom.xml**. Серверный JAR включает драйвер; отдельно скачивать его не нужно. Клиент и common не имеют зависимости от JDBC.

Для новой установки скопируй **db.example.properties** в **db.local.properties** и укажи свои данные подключения, включая пароль БД. Пример использует localhost:8000 для SSH-туннеля. Если локальный файл уже настроен, сохрани его. Файл исключён из Git и не загружается при клонировании репозитория. Java-код не содержит пароль.

1. Открой PowerShell и оставь работающим SSH-туннель:

   ~~~powershell
   ssh -N -L 127.0.0.1:8000:localhost:5432 -o ExitOnForwardFailure=yes -l s505412 -p 2222 se.ifmo.ru
   ~~~

   Если твой туннель уже работает, второй запуск не нужен. Пароль вводится в SSH. Порт 8000 компьютера перенаправляется на PostgreSQL на стороне Helios.

2. В другом окне, из корня проекта:

   ~~~powershell
   mvn clean verify
   java -jar server\target\server.jar --check-db
   java -jar server\target\server.jar
   ~~~

3. В третьем окне:

   ~~~powershell
   java -jar client\target\client.jar localhost 8080
   ~~~

4. В клиенте введи register, затем логин и пароль приложения. После успешной регистрации вход выполнен автоматически. Затем попробуй help, add, show и execute_script examples/demo.txt.

Пароль приложения и пароль для подключения к studs — разные вещи. DbConfig относится к подключению сервера к PostgreSQL. Credentials относится к пользователю программы.

Остановка клиента: exit или конец ввода. Остановка сервера: Ctrl+C. Команда save отсутствует: успешные изменения сразу фиксируются в БД.

## Конфигурация и IntelliJ IDEA

DbConfig.fromEnv() выбирает каждую настройку в таком порядке:

| Настройка | Свойство JVM | Переменная окружения | Поле в локальном файле |
|---|---|---|---|
| JDBC URL | db.url | DB_URL | url |
| Пользователь БД | db.user | DB_USER | user |
| Пароль БД | db.password | DB_PASSWORD | password |
| Путь к файлу настроек | db.config | DB_CONFIG | — |

Если URL нигде не задан, используется jdbc:postgresql://localhost:9000/studs. В db.example.properties используется порт 8000. Пользователь и пароль должны быть заданы. Пустой пароль допускается, отсутствующий — нет.

Файл db.local.properties ищется в рабочем каталоге и до трёх уровней выше. Поэтому запуск ServerMain из корня проекта или модуля server работает с одним файлом. Для произвольного рабочего каталога укажи DB_CONFIG с абсолютным путём.

Для новой установки используй db.example.properties как образец. Существующий настроенный файл заменять не нужно. Локальный файл с паролем не является зашифрованным хранилищем; его не включают в репозиторий или общий архив исходников.

В IDEA открой корневой pom.xml как Maven-проект и выполни Reload All Maven Projects. Запускаемые классы:

- server.ServerMain, classpath модуля server;
- client.ClientMain, classpath модуля client.

Если видишь No suitable driver, обнови Maven-проект и проверь classpath именно модуля server. Если DbConfig сообщает об отсутствующей настройке, проверь рабочий каталог или DB_CONFIG.

## Запуск на Helios

Для простого запуска скопируй server.sh и client.sh в ~/Lab_7 рядом с проектом
или готовыми JAR. Скрипты сами находят JAR в корне либо в server/target и client/target.
Из ~/Lab_7 запусти в первом SSH-окне:

~~~sh
bash server.sh
~~~

При первом запуске введи пароль PostgreSQL. После успешной проверки он сохраняется
в .helios-db-password с правами 600 (доступ только владельцу). Файл исключён из Git.
При следующих запусках пароль считывается автоматически. Для изменения пароля:
bash server.sh --password.

Во втором SSH-окне, также из ~/Lab_7:

~~~sh
bash client.sh
~~~

Скрипты используют порт приложения 18080. Сервер подключается к pg:5432;
старые настройки туннеля в db.local.properties не мешают запуску.
Для остановки сервера нажми Ctrl+C, для клиента введи exit.

Ниже приведён ручной способ запуска без скриптов.

Собранные client.jar и server.jar работают на Java 17 и новее. На Helios сервер подключается к pg напрямую; туннель localhost:8000 нужен для запуска сервера на твоём компьютере.

После переноса JAR в ~/lab7:

~~~sh
cd ~/lab7
export DB_URL='jdbc:postgresql://pg:5432/studs?currentSchema=s505412'
export DB_USER='s505412'
read -s -p 'Пароль PostgreSQL: ' DB_PASSWORD
echo
export DB_PASSWORD

java -jar server.jar --check-db
java -jar server.jar
~~~

Команда read выше предназначена для bash. При необходимости сначала запусти bash. В другом SSH-окне:

~~~sh
cd ~/lab7
java -jar client.jar localhost 8080
~~~

Проверь java -version: нужен JDK/JRE не ниже 17. По умолчанию сервер использует UDP-порт 8080. Если он занят:

~~~sh
java -jar server.jar 18080
java -jar client.jar localhost 18080
~~~

Второй необязательный аргумент сервера задаёт адрес привязки: server.jar 18080 127.0.0.1. SERVER_PORT задаёт порт, если аргумент не указан.

Для одной схемы запускай один сервер приложения: его память содержит загруженную коллекцию. Другие процессы не должны редактировать таблицу routes во время работы этого сервера. После ручных изменений БД сервер нужно перезапустить.

## Схема PostgreSQL

SQL для новой установки находится в server/src/main/resources/db/schema.sql. Твои существующие users и routes уже соответствуют используемым полям; сервер не удаляет и не пересоздаёт их.

На Helios скрипт можно применить так, находясь в каталоге исходников:

~~~sh
psql -h pg -d studs -U s505412 -v ON_ERROR_STOP=1 --single-transaction -f server/src/main/resources/db/schema.sql
~~~

Сначала SELECT current_database(), current_user, current_schema(); должен показать нужные базу, пользователя и схему. Скрипт использует текущую схему. Не создавай таблицы в другой базе вроде ucheb вместо studs.

users хранит id, уникальный login, password_hash. routes хранит все поля Route и owner_id с внешним ключом на users(id). Для обеих таблиц ID выдаёт отдельная sequence. Индекс routes_owner_id_idx ускоряет поиск записей владельца.

Поля to_x, to_y, to_z либо все заполнены, либо все NULL. distance может быть NULL или больше 1. creation_date имеет тип TIMESTAMPTZ(3), совместимый с миллисекундной точностью java.util.Date.

## Ввод команд и элементов

После входа доступны все команды варианта Lab 6:

| Команда | Действие |
|---|---|
| help | Справка |
| info | Тип коллекции, время инициализации, количество |
| show | Все маршруты всех пользователей |
| add | Добавить свой маршрут |
| update id | Изменить свои данные маршрута с этим ID |
| remove_by_id id | Удалить свой маршрут |
| clear | Удалить все свои маршруты |
| add_if_min | Добавить, если дистанция строго меньше глобального минимума |
| remove_greater | Удалить свои маршруты с большей дистанцией |
| remove_lower | Удалить свои маршруты с меньшей дистанцией |
| remove_any_by_distance число/null | Удалить один свой маршрут с такой дистанцией |
| group_counting_by_coordinates | Количество всех маршрутов по координатам |
| filter_contains_name подстрока | Все маршруты, имя которых содержит подстроку |
| execute_script путь | Выполнить UTF-8 скрипт |
| logout | Забыть учётные данные на клиенте |
| exit | Закрыть клиент |

add, update, add_if_min, remove_greater и remove_lower читают данные элемента со следующих строк:

1. name — непустая строка;
2. coordinates.x — Float > -176, NaN запрещён;
3. coordinates.y — Long;
4. from.x — long;
5. from.y — Double;
6. from.z — Long;
7. y или n: задаётся ли to;
8. если y: три строки to.x, to.y, to.z;
9. distance — Long > 1; пустая строка или null означает отсутствие значения.

В скрипте не пишут буквальные {element}. Каждое поле занимает отдельную строку. Пример находится в examples/demo.txt.

Пути вложенных скриптов отсчитываются от родительского файла. Поддерживаются пробелы в пути и внешние двойные кавычки. Строки команд, начинающиеся с #, являются комментариями. Ошибка останавливает текущий файл, после чего продолжается родительский файл или консоль. Циклы включения запрещены, максимальная вложенность — 16. Недостающие поля в конце файла не считываются из консоли.

Маршруты в TreeSet упорядочены по distance, затем по id. NULL меньше заданной дистанции. Условия add_if_min/remove_greater/remove_lower сравнивают именно distance: новый объект ещё не имеет ID. При одинаковой дистанции add_if_min не добавляет объект. Если коллекция пуста, он добавляется.

## Как устроен сервер

~~~text
DatagramSocket
    |
new Thread: получение UDP-пакетов
    |
new Thread для чтения и проверки собранного CommandRequest
    |
CachedThreadPool обработки
    |-- AuthService: проверить логин/пароль
    |-- RequestJournal: исключить повторное выполнение UUID
    |-- CommandRegistry: выбрать ServerCommand
    |-- CollectionService:
    |      synchronized (обёртка коллекции)
    |          проверка владельца и условия
    |          RouteRepository -> SQL -> COMMIT
    |          обновление TreeSet и индекса ID
    |
CachedThreadPool отправки
    |
DatagramSocket -> клиент
~~~

Паттерны использованы там, где они сокращают повторение:

- Command: CommandRegistry и ServerCommand отделяют команды от транспорта.
- Repository: PostgresRouteRepository и PostgresUserRepository содержат SQL.
- Factory: ConnectionFactory выдаёт отдельное JDBC-соединение.
- Шаблон выполнения транзакции: Database централизует commit, rollback и закрытие ресурсов.
- Передача зависимостей через конструкторы позволяет проверять CollectionService без настоящей БД.

Два CachedThreadPool созданы отдельно через Executors.newCachedThreadPool(). Число активных запросов дополнительно ограничено семафором до 64, а одновременных соединений БД — до 16. Завершённые потоки пула переиспользуются; чтение объектов использует новые Thread, как требует задание.

Коллекция — Collections.synchronizedNavigableSet(new TreeSet<>()). Итерация, stream и составные действия выполняются под монитором этой же обёртки. Внешний код получает неизменяемый снимок. Индекс byId защищён тем же монитором и ускоряет поиск при update/remove_by_id.

Блокировка охватывает проверку условия, транзакцию и обновление памяти. Поэтому два add_if_min не сравнят себя с устаревшим минимумом. Цена простого корректного решения: изменения коллекции выполняются последовательно, а читатели ждут завершения текущей записи.

## Авторизация, БД и повторные запросы

Каждый сетевой CommandRequest содержит Credentials. Сервер проверяет пароль по users при каждом запросе, включая повторную доставку. Исключение — REGISTER, создающий учётную запись. LOGIN проверяет её. Все команды коллекции, включая help и info, требуют входа.

Пароли приложения хранятся как saltHex:hashHex, где hash = SHA-256(salt || UTF-8(password)), соль — 16 случайных байтов. Проверка использует MessageDigest.isEqual. Пустой пароль разрешён, пробелы в пароле сохраняются. Логин ограничен 128 символами, пароль — 1024. Credentials и User не выводят пароль или хеш в toString.

owner_id берётся из результата проверки пользователя. В RouteData этого поля нет. SQL UPDATE/DELETE дополнительно содержит условие owner_id = ?, даже после проверки в памяти. Значения передаются через PreparedStatement.

Данные маршрутов читаются из PostgreSQL при запуске. show, info, фильтрация и группировка работают с памятью. Запрос к users для проверки пароля выполняется отдельно и не является загрузкой коллекции.

При отклонённой транзакции память остаётся прежней. Если во время commit оборвалась связь и результат неизвестен, коллекция перестаёт обслуживать запросы до перезапуска. Это предотвращает выдачу потенциально устаревшего состояния. После перезапуска данные снова загружаются из БД.

UDP не гарантирует доставку. Клиент повторяет запрос до трёх раз с тем же UUID. RequestJournal возвращает сохранённый ответ вместо повторного INSERT/DELETE. Журнал находится в памяти и хранит записи пять минут; он не переживает перезапуск. При окончательном тайм-ауте клиент сообщает, что результат неизвестен. Нельзя обещать выполнение «ровно один раз» при произвольном перезапуске и разрыве сети.

Сообщения разбиваются на фрагменты по 1200 байт. Порядок и дубликаты фрагментов не важны. Максимальное сообщение — 2 МиБ; неполные сообщения имеют квоту памяти и срок жизни. Java-десериализация ограничена белым списком классов и проверкой инвариантов моделей.

Логин/пароль передаются в каждом UDP-запросе согласно заданию. UDP-канал приложения не шифруется. При запуске обоих процессов на одном компьютере или на Helios с localhost трафик не выходит на внешний интерфейс. SSH-туннель шифрует участок подключения к PostgreSQL между компьютером и Helios.

## Проверки

Обычная сборка запускает тесты моделей, протокола, клиента, авторизации и коллекции:

~~~powershell
mvn clean verify
~~~

Проверки с настоящим PostgreSQL включаются отдельно. Туннель должен работать, DbConfig должен подключаться к нужной БД:

~~~powershell
$env:LAB7_TEST_DB = 'true'
mvn verify
Remove-Item Env:LAB7_TEST_DB
~~~

В bash:

~~~sh
LAB7_TEST_DB=true mvn verify
~~~

Интеграционные тесты создают только собственные таблицы со случайным префиксом lab7_test_<uuid>_. Им не нужно право CREATE SCHEMA. Рабочие users/routes не очищаются. В конце тестовые таблицы и sequence удаляются.

Проверяются реальные sequence, сохранение NULL и дат, загрузка при повторном создании сервиса, SQL-защита владельца, откат пакетного удаления, параллельная регистрация, конкурентное добавление, чтение из памяти при недоступной таблице routes, обмен по UDP и сообщения больше 65507 байт.

Отчёты JUnit находятся в target/surefire-reports каждого модуля. Краткое объяснение для защиты — в DEFENSE.md.
